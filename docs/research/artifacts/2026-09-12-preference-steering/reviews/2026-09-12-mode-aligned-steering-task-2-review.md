## Evidence

- The public runner validates the candidate, regime, method, feature-kind, beta, and finite-positive proposal subsets; its defaults are mode features, M=8/32/128, soft and best, L=4, beta=16, N=16, all canonical synthetic users, and both regimes (`env/run_mode_ablation.py:173-214`, `env/run_mode_ablation.py:431-453`). It loads the demonstration bank only to compute the train digest, loads the checkpoint and statistics once with that expected digest, freezes/evaluates the policy, and snapshots policy/stat state for the final integrity check (`env/run_mode_ablation.py:223-244`, `env/run_mode_ablation.py:408-427`).
- The resolved config is atomically created before any `_closed_loop` condition executes and binds the selected experiment dimensions, checkpoint/stats/demonstration/train-data hashes, execution-source hashes, thread count, environment, and changed proposal distribution. An existing unequal config is refused (`env/run_mode_ablation.py:246-285`). The CLI defaults to one Torch thread and leaves GPU use explicit through `--device` (`env/run_mode_ablation.py:435-468`).
- Each condition key includes regime, profile, selector, and M. Environment and rollout seed arrays are derived once and passed unchanged to every condition, and `_closed_loop` preserves them in each NPZ (`env/run_mode_ablation.py:309-318`, `env/run_mode_ablation.py:355-368`; `env/run_grouped_preference.py:101-102`). Conditions are processed and released one at a time (`env/run_mode_ablation.py:337-406`).
- Proposal scaling occurs after deterministic latent generation and only when `method != 'base'`; current candidates are scaled while future tensors remain untouched. The copied output therefore contains actual scaled currents, while raw base continues to use candidate-zero unit-normal draws (`env/run_grouped_preference.py:26-47`, `env/run_grouped_preference.py:50-63`, `env/run_grouped_preference.py:120-140`). `feature_kind` is forwarded into conditional evaluation and actual-path metrics, so the scored features, saved expected features/utilities, and diagnostics use the selected semantics (`env/run_grouped_preference.py:124-140`; `env/run_mode_ablation.py:355-372`).
- The learned grouped runner exposes the same finite-positive option in its API and CLI, records its value and the base/guided/future distribution distinction, and forwards it to all conditions; `_closed_loop` itself keeps the base exception (`env/run_grouped_preference.py:267-292`, `env/run_grouped_preference.py:316-324`, `env/run_grouped_preference.py:370-388`, `env/run_grouped_preference.py:403-426`).
- Completion is crash-safe at the condition level: NPZ and JSON use same-directory temporary files, fsync, and atomic replacement (`env/run_mode_ablation.py:42-74`). Before any completed condition is skipped, its marker metadata, artifact existence/digest/field manifest, embedded metadata, and record digest are validated (`env/run_mode_ablation.py:140-170`, `env/run_mode_ablation.py:319-335`). An NPZ without its completion marker is rerun and atomically replaced, and diagnostics are flushed after every completed condition before the final source/policy/stats integrity gate (`env/run_mode_ablation.py:337-427`).
- Target metrics classify the midpoint of actual Gym paths, intersect the target mode with complete successful episodes, divide by all paired episodes, compute a 95% Wilson interval, and report reached-path plus successful-path distributions over all four modes and `other`. Early failures remain visible through the explicit denominators and the existing incomplete/numerical/action-limit metrics (`env/run_mode_ablation.py:88-129`; `env/run_grouped_preference.py:177-227`). Each condition also records elapsed time, total task failures, and fallback diagnostics, and progress output flushes through the CLI callback (`env/run_mode_ablation.py:369-405`, `env/run_mode_ablation.py:467-468`).
- Behavioral tests cover exact guided-current scaling with unchanged future streams and base current draws, invalid scales, real selector divergence, goal-miss exclusion, paired M-prefix streams, complete-condition metadata, resume equivalence, mismatch/corruption refusal, partial artifact replacement, and continuous-feature propagation (`env/tests/test_run_mode_ablation.py:73-272`).

## Non-blocking observation

- The Python API checks that user keys are canonical and values are `GroupedPreference` instances, but it does not require each supplied value to equal the canonical preference associated with its key (`env/run_mode_ablation.py:209-214`). The CLI always constructs the canonical mapping (`env/run_mode_ablation.py:444-466`), and every actual preference is persisted, so this does not affect the specified CLI experiments. Tightening that API check would prevent a custom caller from accidentally pairing a canonical target-mode name with different weights.
